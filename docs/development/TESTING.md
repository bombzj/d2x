# 测试与验证

围绕本次问题和改动影响选择验证方法，先读[项目基线](../../BASELINE.md)和负责专题。默认不构建、运行或打包，按用户有效授权执行；已授权任务中的必要修复、重编译和复测沿用该授权。不新增测试脚本、测试用例或专用测试程序，复用现有游戏、资源工具和调试入口。

## 工作思路

先明确操作、预期结果和观察对象，再从便于复现的入口收集证据。需要核对原版行为时，对照相近条件下的实际操作与消息，并参考本地 D2MOO 和当前 MPQ 定位差异；修复后复测原问题，再按影响补充回归。顺序可随问题和已有证据调整。

## 按场景选择

以下是常用选择，具体组合与覆盖范围由本次任务决定。

| 场景 | 可考虑的方法 |
| --- | --- |
| 玩法／消息差异 | 在 D2X Host 复现并记录 C2S／S2C；用 D2X Join 原版 Host 采集同类操作作为对照，结合权威事实定位差异 |
| 客户端／UI表现 | 用图形客户端实际操作，结合收到的原包、副本和截图；必要时分别连接原版与 D2X Host，区分客户端和宿主问题 |
| 原版兼容／多人交互 | 用原版 Join D2X Host，或多个真实 TCP 客端；按问题选择连续操作、旁观者、加入退出、私有消息等场景 |
| 保存／恢复 | 使用隔离角色，正常保存退出后以新进程重入，核对相关持久值和拒绝条件 |
| 时序／负载／传输差异 | 按需使用 headless、宿主暂停／单步或多客户端；涉及单机与 TCP 差异时分别观察。headless 不验证图形和 UI |

入口与参数见[构建／运行](BUILD_AND_RUN.md)和[调试管道](DEBUG_PIPE.md)。原版规则的参考范围见[资料来源](../resources/THIRD_PARTY.md)。

## 重点注意

- **确认测试版本**：区分当前源码、已有 EXE 和历史结果，记录必要的配置、MPQ及角色条件。构建期间若相关源码或公共头变化，应重编译受影响单元；使用明确身份的 EXE 副本可避免测试期间产物被替换。构建要求见[构建验收](BUILD_AND_RUN.md#构建验收要求)。
- **分清提交与结果**：命令 accepted／queued 只表示受理或入队。原包、客户端副本、权威快照／事实和实际画面各有观察范围；结合需要确认操作是否执行、消息是否收到及表现是否正确。
- **对照条件要可解释**：注明原版版本及 Host／Join 角色。比较包型、字段、顺序和最终行为；GUID 等动态字段可在有依据时归一化，保留原始数据与归一规则。不同种子、装备或人数下的随机结果不宜直接判为缺陷。
- **准备条件单独说明**：管理旅行、生成物品／怪物、补资源可用于复现；这些操作不能证明自然生成、正常获得流程或掉落概率。原服不具备自研宿主管理和单步能力。
- **保护与收尾**：隔离存档、管道和端口，保留用户已有进程与文件。失败先保存现场；退出时确认正常保存和离局结果，再关闭本项进程。暂停的宿主可能需要恢复或单步完成待办。

## 结果与文档

交付时简要说明实际条件、操作、预期与结果，以及失败和未覆盖范围。临时日志、截图、构建产物和隔离存档放忽略目录，不纳入源码提交。

发现缺陷后更新负责专题中的当前实现、原版依据和限制；证据应有可独立定位的版本、函数／字段或实机条件。结论限于实际覆盖，不把单机、自研运行或某个平台的结果扩大为全面一致性，也不重复追加过程流水或验证等级。
