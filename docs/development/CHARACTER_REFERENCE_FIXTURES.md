# 原版人物数值对照存档

## 目标与交付边界

使用原版资料片客户端的实际显示建立独立标准答案，再让真实 D2X 客户端从相同初始 D2S 副本入局、执行指定操作、读取面板同源视图并逐字段对比。首先验证人物属性面板与选定技能的说明数值，不把显示正确推定为实际战斗正确。

首批已从当前 MPQ 生成 **22 个带装备存档**：下文 16 个主要归属，加上两个套装阈值及四个抗性／等级变体，共 436 件根物品、56 件孔内物品。22 个角色均已由本机原版单机载入并正常保存；已采集 27 个人物面板场景、七职业代表技能说明及 58 张原版原生截图。27 个场景已由真实 D2X 图形客户端和嵌入宿主分别取值比较；完整机制矩阵仍有待采项。没有裸装专用存档，不要求每个职业重复携带同类护符或镶嵌物。

源码、协议和当前限制见[人物模块](../modules/CHARACTER.md)、[属性](../gameplay/characters/ATTRIBUTES.md)、[物品目录](../gameplay/items/README.md)、[技能描述](../gameplay/skills/DESCRIPTIONS.md)；执行与验证授权见[测试指南](TESTING.md)。本文维护存档装配、独立原版依据、实际覆盖与未核实边界，不提供测试脚本、单元测试或专用测试程序。

## 去重与覆盖方法

覆盖单位是**属性效果及其处理路径**，不是物品名称、每条词缀或每件装备。先建立需求矩阵，再选择覆盖更多未覆盖项、操作更少的合法物品组合。每个覆盖项有一个主要样本归属；其他物品自然重复的属性保留，不为去重删除原物品属性或制造非法组合。

建议覆盖键记录：`品质 / 属性来源 / stat与参数层 / 消费路径 / 生效条件 / 边界`。

- 同品质、同来源路径、同参数含义的相同属性，普通代表样本一次即可；数值范围内的不同掷值不按新机制重复截图。
- 同一效果不必在小／大／超大型护符各测一遍；三种尺寸各至少一个合法代表，所有护符的不同效果分散装配即可。技能页护符还须记录其页参数，不能把任意页编号合并为一个已通过项。
- 一颗填料可提供多个效果。按当前 `Gems` 的武器／头盔与盔甲／盾牌槽分别登记；同名填料在不同槽并不自动等价。珠宝的宿主相关伤害计算也单列。
- 普通品质的基底伤害／防御，超强品质的增强层，魔法／稀有的词缀层，Crafted 的固定配方与随机词缀层，暗金／套装的特殊记录层，孔内与符文之语层不能互相替代。
- 已核实共用同一消费路径后，不机械展开全部“品质 × 属性 × 职业”。但也不能用魔法装备的力量通过，认证稀有、暗金或 Crafted 的属性解码。每种品质先覆盖自身身份／属性层入口，再按独立路径补差异。
- 有明确交互的组合保留：百分比与平加顺序、武器与非武器增强伤害、最小／最大伤害、毒伤率与持续时间、技能加成与基础协同、套装阈值、需求链、切组和失效后的贡献撤销。
- 最终总值是判定目标。多个效果可能相互抵消，因此关键边界使用非对称值及一个指定变化场景；无需为诊断增加裸装档。

矩阵不能只记录“物品存在”。还要标明效果是否活动、哪个观察字段会受影响、如何取得原版依据。只有物品说明可见、但没有最终结果观察入口的效果，不计入人物面板已覆盖。

## 资源、人物与装备约束

- 原版目标为本机 1.13c 资料片；每批实际记录原版 DLL 与当前五个 MPQ 的 SHA-256、覆盖顺序、语言。当前资源入口是 `assets/mpq2`，摘要参考[MPQ](../resources/MPQ.md)，交付时重新记录实际文件，不能仅凭版本文字认为相同。
- 装配清单动态来自当前 MPQ 的 `CharStats`、`Experience`、`Skills`、`SkillDesc`、`Weapons`、`Armor`、`Misc`、`ItemTypes`、`ItemStatCost`、`Properties`、词缀、`AutoMagic`、`UniqueItems`、`SetItems`、`Sets`、`Gems`、`Runes`、`CubeMain`、`Inventory` 等表。参考仓库附带参数不作生成输入。
- 所有角色均有合法活动武器／职业武器及防具；非专项槽用简单合法装备，不刻意塞满增益。选装需要的力量、敏捷、等级、职业和技能前置先满足，需求失效仅留在指定边界场景。
- 七职业主档暂按 80 级设计，最终等级和点数由选装需求与技能预算确定。属性和技能点总量守恒；基础等级、有效等级和协同基础等级刻意区分。不制造所有技能 20 级但没有对应点数的档。
- 普通场景不带佣兵、不召唤伙伴、不携带随机触发增益；指定召唤／变身／光环场景单独记录。永久任务奖励默认无，只有抗性专项明确配置并记录对应任务／消耗位。
- 默认普通难度、第一幕城镇、主武器组、资源补满后观察。噩梦／地狱使用明确解锁的合法进度；记录人物实际难度而非只看存档标题。资源恢复、切装前后限制和补满过程列为步骤，不假定载入即满。
- 名称使用 2–15 个 ASCII 字母，避免原版与 D2X 命名差异。所有实际品质、特殊记录、词缀编号、参数层、掷值、基础防御、耐久、无形、孔数、子项顺序、位置和武器组写入清单。

| 四抗 | 单抗／全抗、永久奖励、装备／状态、难度惩罚、上下限与最大抗性 | P04、P11、P14–P15 |
| 技能来源 | 全技能、职业、技能页、单技能、StaffMods、AutoMagic、跨职业授予、充能 owner | P01–P07、P12–P14 |
| 条件贡献 | 套装层、符文之语层、护符位置、孔内顺序、需求／耐久／鉴定、切组 | P05、P09–P16 |
| 技能描述 | 法力／伤害／时间／数量／范围，当前与下一等级、跨技能引用、基础协同与有效等级 | 七职业主档＋专项 |

“平加伤害”“忽略防御”“吸收”等效果是否进入原版面板必须按原版核实；不能把本表的类别名称等同于所有同类 stat 都可用截图认证。物品说明、人物显示、实际战斗分别登记。武器数值即使显示正确，也不认证命中、吸取或目标抗性结算。

### 不能靠人物截图验证最终效果

FCR／FHR／IAS／FBR、移动速度、吸血／吸魔、压碎／致命／撕裂、目标防御与抗性修改、伤害减免／吸收、再生、攻击触发、MF／GF 等保留独立覆盖项；能在物品说明看到某属性不等于已验证其最终效果。

- 速度类需要原版动作帧数／时序依据；百分比手工求和只可检查来源清单，不作最终行为标准答案。
- 战斗类需要固定目标、难度、人数、状态和足够精度的原版观察；怪物原包生命比例不能直接充作精确伤害。
- 随机类需要明确统计设计；本批固定物品不能认证掉落、触发概率或随机算法。
- 隐藏总值可另行核实原版公共函数／内存观察方案，但获得原版独立证据前保持未采集。

这些属性可随选装自然出现，先记录清单，不强行删除；其存在不能扩大本批测试通过范围。

## 护符与镶嵌的具体去重规则

护符统一由 P14 为主要覆盖档，其他档仅为未覆盖的技能页／边界需要携带，不统一复制一套护符。至少覆盖三种尺寸、魔法前后缀、技能页参数、合法暗金身份、背包生效与非背包不生效。实际效果从当前允许的词缀／特殊记录筛选；普通同类掷值范围不逐档重复。

宝石与符文先从当前表列出“填料 × 宿主槽 → Properties／参数／计算路径”。相同等级曲线、相同效果和路径可选代表，不把每个等级当作新测试；不同元素、毒持续、符号、参数层和宿主映射保留。P09／P10／P11 分别容纳三个槽族；头盔和盔甲经当前表确认共用同一槽后可以去重。

珠宝区分魔法与稀有身份、多个属性、武器局部与非武器全局伤害贡献。保留原版实际组合，不任意捏造 ED／最小／最大伤害词缀。符文之语由 P12 单独覆盖，包含宿主本体、孔内符文和独立符文之语属性；正常符文排序与不成词的负向样本仅在当前表与原版资格已明确时配置。

至少一个混合场景同时含装备本体、孔内填料、护符和技能／状态，验证总和；它可以落在已有档里，不另设仅为重复贡献的存档。

## 技能采集的控制规模

七职业主档各先选一个有代表性的技能说明，附人物左右技能动作值；不能因此宣称全职业 210 项技能通过。后续按 `SkillDesc` 描述程序／公式与特殊执行路径扩展，尤其覆盖：

- 普通元素、物理来源、持续火焰、毒总量、召唤数量与属性、光环／增益、武学充能、变身。
- 基础等级与有效等级不同、装备加成不充当基础协同、全技能／职业／页／单技能叠加及来源撤销。
- 当前／下一等级、跨技能引用以及等级曲线分段边界；等级值从当前规则核对后确定。
- 城镇不可施放的状态到固定安全位置建立；有计时、充能或伙伴依赖的场景不能仅靠存档表示。

不要在每个主档同时建立多种暂态再截图。每次只执行场景列出的变化，记录已确认的状态，而不是“等几秒应该好了”。为边界确需不同基础等级时，从冻结配方生成独立合法变体，不在截图过程中让用户随意加点。

## 数据、截图与脚本契约

### 每个存档与场景必须记录

- 存档：稳定 ID、姓名／职业／等级、原始 D2S SHA-256、MPQ／原版版本摘要、地图种子、模式、进度、三难度永久奖励、属性与技能预算、全部物品及容器位置、生成工具及配方摘要。
- 场景：稳定 ID、初始副本、难度、武器组、左右技能及 owner、操作顺序、场景到达条件、当前状态／伙伴、观察字段、截图名称与必要悬停位置。
- 标准答案：从原版截图逐字段抄录的值、上下限／单位／小数精度、截图依据；缺失值为 `null` 并有原因，不填 D2X 算出的结果。
- 实际结果：D2X 源码／EXE 身份、客户端同源视图、请求确认与状态、失败原因；自研权威快照作为附加诊断，不能代替客户端实际值。

使用不同文件保存生成配方／覆盖清单、原版 expected、D2X actual 与比较报告。原版收包作为输入诊断单独保存，D2X 接原版 Host 的本地显示仍是 D2X 计算，不能自动录入 expected。

### 判定规则

整数显示严格相等；伤害上下限分别比较；小数以原版实际显示精度和截断规则比较，不设通用容差。数值、单位和技能等级来源分开保存，不能从字符串模糊匹配得出通过。

结果至少区分 `pass`、`mismatch`、`missing_reference`、`unknown_actual`、`setup_failed`、`unsupported`。缺标准答案、D2X 问号、请求未确认或未实现都不能计作通过。可见字段通过不推定其他隐藏效果通过。

对照执行调用真实 D2X 入局及命令路径，读取人物面板／技能说明的同源结果，不在脚本里复制公式。人物 `CharacterView` 可由现有诊断取值，技能描述可读取同源skills中的树／选择器提示；数值采集使用只读出口，不旁路客户端计算。

这属于“D2S → 自研宿主 → 原包 → 客户端投影”的端到端数值对照。若只读取同源视图，文字排版、字体和像素仍需截图验收；真实战斗结算另立场景。

### 原始资料管理

计划文档与对比逻辑可纳入源码；存档、原表、原版截图、收包、运行日志及个人数据保存在忽略目录 `artifacts/character-reference/`。建议分为 `tables/`、`recipes/`、`originals/`、`screenshots/`、`expected/`、`runs/`；每次运行复制原始档，原件不被游戏退局覆盖。

expected 数据先与截图证据保存在同一批次；需要长期回归时，只提升已核对且无个人数据的数值及资源身份到源码数据目录，不提交 D2S 或资源。原件、样本变体及原版正常保存后的文件各自保留校验值，不静默把规范化后的档替换原件。

## 生成途径与当前缺口

已静态核对的当前入口：

| 入口 | 可复用内容 | 当前不足 |
| --- | --- | --- |
| `hosting/character_creation.cpp::createCharacter` | 当前 MPQ 创角、初始库存与原身份 | 没有批量配方／定点装配 CLI |
| `hosting/item_content.cpp::prepareItem` 及内容生成器 | 真实品质／词缀／特殊记录／固定掷值准备 | 要绑定原合法选择与明确随机状态；不能把种子或支持失败静默略过 |
| `persistence/save_codec`／`save_file` | 原 v96 编码、人物／任务预算校验、真实孔内物品保存 | 不接受任意越界或非法组合；不能修改校验来放行样本 |
| `d2x_assets save-recipes`／`save-json`／`save-info` | 离线批量装配、原 v96 编码／重读及只读 JSON／摘要导出 | 配方格式与支持边界见下文；不自动操作游戏、不提供人物显示 expected |
| `item-spawn`、`grant-experience`、正常学习／装备／镶嵌及保存 | 经现有宿主准备合法角色和物品 | 管理入口不能精确指定词缀／特殊行／掷值，也不提供 Crafted 品质；不适合靠随机反复尝试覆盖矩阵 |
| 本地 `reference/d2s-validation` 的外部 D2S 编码器 | 交叉读取／编码的候选工具 | 默认自带表不代表当前 MPQ；未核对字段和表绑定前不用于批量造物品 |

已在现有资源工具增加**离线存档配方生成入口**，实现位于 `src/asset_save_recipe.cpp`，复用 `createCharacter`、`prepareItem`、词缀／特殊物品／镶嵌准备和原 v96 codec。不新写 D2S／JM 编码，不引入第二套人物属性公式，不更改玩法、协议或存档语义。使用方法：

```powershell
.\build\bin\d2x_assets.exe assets/mpq2 save-recipes artifacts/character-reference/recipes/batch.json artifacts/character-reference/new-batch
.\build\bin\d2x_assets.exe assets/mpq2 save-json artifacts/character-reference/originals/RefAmazon.d2s artifacts/character-reference/amazon-export.json
```

输出路径必须不存在。`save-recipes` 先在内存准备全部人物、编码并重读，再输出 D2S 和 manifest；文件 I/O 失败会保留现场目录，重试使用新目录。`save-json` 只读输入档，拒绝覆盖输出 JSON。

配方 `schema:1`、`characters[]` 每项指定唯一 `id`、2–15 个 ASCII 字母的 `name`、`class`、`level`、`mapSeed`、`allocated:[力量,敏捷,体力,精力]`、按 MPQ 技能原名索引的 `skills`、可选 `leftSkill`／`rightSkill` 和 `items[]`。余点由当前 CharStats 及已分配值计算，再由 codec 校验经验、预算与前置。`difficulty:1/2` 配置低难度五幕首领完成及跨幕进度；仅 `resistanceRewards:[难度索引]` 明确设置抗性卷轴发放／消费位，不附带其他永久成长奖励。

当前源码增加可选整数`gold`／`bankGold`，省略时保留原创角余额；要求非负且分别不超过等级×10000的钱包上限及公共`stashGoldLimit`，manifest／save-json输出实际余额。不改变v96格式、存档校验或运行中的授金入口。用于[第一幕调试女巫配方](fixtures/debug-act1.json)的购买准备；新增字段与该配方已通过Windows Release构建、原v96编码／重读及独立入局；任务运行覆盖见[调试AI](DEBUG_AI.md#实现入口与待验收范围)，不沿用本页其他角色比对结果。

物品指定 `code`、`quality`、`level`、32 位 `seed`；`location` 为 `equipment`／`backpack`／`stash`／`cube`，装备另给原 `slot` 与可选手部 `weaponSet:1`。网格按当前 Inventory 首个空位放置。特殊品质用精确 `special` 原名；魔法／稀有可用已有合法 `properties:[{code,parameter?,value}]` 或非直接属性的 `min/max` 选择器。Crafted 另给 `cubeRecipe` 的原行号和 `inputLevel`，检查基底、配方条件及输出等级后应用固定层。`children[]` 按顺序生成填料，检查孔数和类型，再经现有符文之语准备；`runeword` 可明确核对最终原名。`ethereal`、`identified:false`、`broken:true` 仅用于明确样件。

该入口检查槽位／职业、等级、容量、品质来源及既有 codec 边界；不替代完整装备资格链与各状态的原版采集。新装配须按矩阵确认基础需求、双手组合、单件携带限制及场景生效条件。未知来源明确暂缓。

Crafted 必须使用有效 `CubeMain` 配方的固定层与合法随机词缀，不能仅设置品质枚举。套装条件层、珠宝、StaffMods／AutoMagic、无形／超强、每等级 stat、充能及符文之语都要输出实际身份与值；未知来源明确暂缓。

生成实施顺序：

1. 从当前 MPQ 导出所需表和摘要，扫描合法来源／可见消费路径，形成候选与未覆盖矩阵。
2. 定下具体装备、配方、技能与预算，装配到上述档；不能装入的项拆档。先冻结 manifest，再输出 D2S。
3. 用已有 codec 重新读取新档，核对身份、点数、槽位、掷值、子项顺序和 manifest 一致性；这是生成完整性检查，不是数值通过证据。
4. 原版由用户或明确获授权的 UI 操作实际打开档；原版拒绝／改写时保留原文件与原因，修复生成方案，不修改原 MPQ。分别冻结原版接受后的基准版本。
5. 按场景采集原版截图，录入 expected，再实施／运行 D2X 对比。原版接受存档仅证明准入，不证明全部效果和数据正确。

每次生成与比较分别记录实际源码、EXE、MPQ和输入档身份，不能用旧EXE生成成功认证当前源码。授权与验证范围统一遵循协作约定和测试指南。
