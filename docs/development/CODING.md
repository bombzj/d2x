# 编码约定

先读[项目基线](../../BASELINE.md)、[架构速览](../architecture/OVERVIEW.md#agent速览)和负责专题，再确定修改位置。沿用附近代码的命名与格式，围绕当前问题修改，保留已有工作。以下约束明确职责与行为；具体实现方式按实际需要选择。

## 重点约束

- **跨平台与分层**：保持 C++20／CMake 的 Windows、Linux 路径。平台 API 留在外围适配；玩法使用已准备的数据，不读取 MPQ、文件、网络、设备或 GPU。客户端读取副本并提交请求；服务端玩法领域负责权威结算，宿主负责资源准备与协议适配。
- **规则有依据**：资源和参数优先取当前 MPQ，原版调用链优先参考本地 D2MOO；发现版本差异或行为矛盾时再定点核对原 DLL。区分数据参数与协议／算法常量；缺资源或依据时明确暂缓，保留真实身份，替身仅按[协作约定](../../AGENTS.md)使用。
- **状态归属清楚**：通过所属领域的接口修改状态，缓存和客户端副本保持派生关系。跨领域协作传递必要数据或窄能力，避免让会话、资源对象或整套系统成为隐式依赖。
- **保持行为语义**：核对整数宽度、符号、固定点、截断／溢出、随机流及消费次序。优化和重构保持有效输入下的数值、时序与副作用；有意改变行为时说明依据与影响。
- **结果如实表达**：区分受理、等待、提交、拒绝和未实现。失败应保留可定位原因，避免吞错、伪造成功或以其他行为代替尚未实现的规则。

## 实现建议

- 优先沿用已有领域入口和纯计算。函数围绕清楚的职责组织，命名表达业务含义；接口难以理解时，可用具名类型或参数结构说明含义。
- 抽象由实际复用、变化或隔离需求驱动。简单分支可以就地表达，独立算法或复杂流程可拆成函数／文件；PImpl、虚接口和额外层次按收益选择。
- 用 RAII 管理资源，明确所有权、共享方式和借用期限。只读或可写借用由接口职责决定；跨异步、提交或容器变化等边界时，采用稳定身份、重新查找或明确的生命周期保障。
- 头文件暴露必要契约，直接包含实际依赖。适合时前置声明、将实现放入 cpp 或领域内部头，减少无关重编译；按值成员、模板或内联实现需要完整定义时保留相应包含。
- 新增编译单元登记到现有 CMake 目标，依赖可见性按消费者需要选择。具体文件布局和私有类型归属由[架构文档](../architecture/OVERVIEW.md)维护。

## 涉及特殊边界时

| 场景 | 注意与建议 |
| --- | --- |
| 延迟执行／事务／背压 | 明确采样、执行和提交时点，按需复验身份、区域、代次及修订。已发生的操作冻结成事实；重试保留已确定结果，避免重复扣费、掷数、命中或奖励，也避免从后续快照反推历史操作 |
| 原协议／存档 | 区分内部模型、网络字段和磁盘格式，沿已有编解码入口处理范围、长度与版本。存档语义变化同步格式、校验及文档，旧档按明确策略处理，不静默迁移 |
| PD2／CN兼容 | 先核对[PD2基线](../pd2/README.md)、目标版本和负责分册，标明 CN 附加行为及未知项。小差异可保留局部分支，大块算法或流程可在所属领域拆分；在明确的适配入口或已准备规则中选择差异，共用状态、时钟和事务，保持原版路径并核对受影响消费者 |

版本隔离的详细边界见[兼容设计](../architecture/PD2_COMPATIBILITY.md)。D2X自行实现规则，不在产品中加载或安装原核心 DLL／Hook；旧地址、函数名或目录分离本身不构成行为等价依据。

## 修改与交付

验证方法与授权边界见[测试指南](TESTING.md)。交付说明实际改动、验证结果和未覆盖范围；规则或结论变化同步负责专题，文档维护事实、入口和限制。

资源、构建缓存、日志、截图、存档及参考仓库不纳入源码提交，保留原始 MPQ、旧压缩包和 mvp/。多人协作时先明确文件与公共接口归属，避免覆盖其他工作。
