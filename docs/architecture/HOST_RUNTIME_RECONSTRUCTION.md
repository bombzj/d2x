# 宿主线程改造简明方案

状态：三个步骤代码与文档已接入；多房间性能、完整后端故障组合及跨平台验收仍有缺口。更新：2026-10-27。

## 原版核对

**单机同步推进、TCP/IP 房主独立服务线程，有原版 1.13c 指令依据；独立游戏服务器具备多队列游戏任务调度机制，但本轮未确认暴雪线上部署的实际线程配置。**

| 模式 | 原版依据 | 结论 |
| --- | --- | --- |
| 单机 | D2Launch 将游戏模式设为 0；D2Client RVA `0x44CEE` 检查模式，模式 0 在 `0x44D00` 调用 D2Game ordinal 10008，即 `GAME_UpdateGamesProgress`，随后继续客户端处理 | 本地服务端可与客户端主流程同线程推进，不必专门创建模拟线程；不代表整个程序只有一个线程 |
| TCP/IP Host | D2Launch 的 Host 按钮表项（TBL 5118，RVA `0x24040`）绑定 `0x1AFA0`，在 `0x1AFA6` 设置模式 8；D2Client `0x45024` 检查模式 6／8，`0x45058` 调用 CreateThread，入口 `0x431B0`，其中 `0x431ED` 调用同一 D2Game 推进入口 | 房主的服务端独立线程运行，不依赖窗口绘制 |
| 独立 GS 多房间 | d2moo 的 [Task.cpp](../../reference/d2moo/source/D2Game/src/GAME/Task.cpp) 包含多任务队列、队列间平衡及 `TASK_ProcessGame`：锁定单局、推进、解锁，再按 40ms 重排；[Game.cpp](../../reference/d2moo/source/D2Game/src/GAME/Game.cpp) 提供单局推进 | 参考其“跨局调度、单局串行”结构实现多游戏线程；任务槽数不是线程数，不能据此声称原版固定开 32 个线程 |

证据身份：d2moo 提交 `5596f5cb6c5251a0a07c6637d26458b06099d516`；原 1.13c D2Client SHA-256 `dd8bc6025de921216a97c17f97cd1a50fbb85926e838ec60e13451448836d906`，D2Launch SHA-256 `99cabc4751c95d035b5e77151b3605b809884fec2c10edf37d4c4e4e231e8479`。以上为静态核对；d2moo 任务创建函数仍带未完成标记，不照抄其链表代码或版本地址。

## D2X 改法

三种模式共用现有 GameHost／GameInstance 和原协议，只改变谁调用宿主推进，不重写玩法。

| 模式 | 线程安排 | 最小化行为 |
| --- | --- | --- |
| 单机 | 保留主线程调用嵌入宿主；世界按单机菜单／失焦策略暂停 | 不绘制；主线程仍定期处理窗口事件、内存协议和心跳，暂停的只是玩法，不是连接服务 |
| TCP/IP Host | 增加一个独立宿主线程，负责收包、25Hz 模拟和发包；窗口线程只负责客户端 | 不绘制；宿主照常运行，房主失焦／ESC 不暂停游戏 |
| 独立战网 GS | 配置固定数量的游戏线程；建房时分配到一个线程，该房间生命周期内不迁移；线程轮流推进自己负责的房间 | 无窗口；多个线程并行运行不同房间，同一房间始终串行 |
| TCP/IP Join／战网客户端 | 不启动本地游戏模拟线程，沿用客户端网络 worker | 不绘制，继续收包及必要的副本处理 |

独立 GS 先按线程负载分配新房间，保留线程数配置及单线程模式，不引入工作窃取、动态迁移、通用 Actor 框架或多进程调度。同一线程上的房间仍会共享 CPU 时间，不承诺绝对互不影响。

## 必要改动

1. **分离事件处理和绘制。** [application.cpp](../../src/app/application.cpp) 已开启 `FLAG_WINDOW_ALWAYS_RUN` 关闭隐式停转；[frontend.cpp](../../src/app/frontend.cpp) 最小化分支处理事件／必要服务后限频等待，跳过绘制、纹理上传及交换缓冲，不是继续后台渲染。
2. **让宿主有明确线程归属。** [embedded_realm.cpp](../../src/hosting/embedded_realm.cpp) 在单机由主线程调用，在 LAN 由独立线程调用，禁止两边同时 pump。UI／调试的建房、暂停、保存、退出通过有界请求队列交给宿主；查询读只读快照，不直接跨线程访问活动对象。沿用有锁内存传输。
3. **按游戏线程拆分多局状态。** [native_realm_host.hpp](../../src/hosting/detail/native_realm_host.hpp) 中的实例、地形、连接投影和可变缓存归所属游戏线程；房间目录只负责路由。可共享已冻结的规则表，MPQ 句柄及可变缓存不能无保护地共享。先采用线程级宿主分片，不给整个服务端套一把大锁。
4. **保留固定步和顺序。** [game_host.cpp](../../src/hosting/game_host.cpp) 继续 25Hz／40ms；每轮限制单房间追赶步数后轮到其他房间，不丢逻辑帧、不改随机与事务顺序。单机暂停期间不积累欠帧；恢复不快进。单局内不并行 AI、碰撞和战斗。
5. **移走会阻塞全部房间的等待。** [pvpgn_server.cpp](../../src/hosting/pvpgn_server.cpp) 通过请求／完成消息连接专用存储线程，DBS单次最长15秒等待不占游戏线程或主线程。区域准备沿既有线程，文件保存归后端工作队列；保存成功后才确认退出，未知结果保留恢复文件、不自动解锁。不扩展存档格式或后端事务协议。

退出时先停止新请求，结算并保存，再结束连接和 join 宿主线程；TCP 房主退出仍先保存／结束客人。跨线程请求和异步结果带实例／连接代次，避免退出重入后误用旧结果。客户端最小化期间继续消费必要的有序事件和 TCP 存档回传，不能无限积压到窗口恢复。

## 实施与验收

按三个步骤实施，每步单独确认：

1. 单机最小化不绘制且继续心跳；TCP/IP Host 独立宿主线程。已实施；当前线程与生命周期见[架构说明](OVERVIEW.md#生命周期)。
2. 独立 GS 固定游戏线程已接入：gameThreads默认2，新房按房间数分配，独占资源和宿主；专用后端线程承担文件／DBS等待。实际并行吞吐仍未测量。
3. 已核对退出保存、暂停恢复、队列上限与分片边界，并更新部署／存档／架构说明；多房间负载及完整后端故障组合仍待验收。

完整验收仍需覆盖多房间实际使用多个核心、单房加载／存储等待时其他分片的持续推进及完整后端故障组合。单机／TCP/IP最小化、正常退出重入仍是后续改动的回归边界；最小化检查应用绘制提交为零，不要求整个进程零 CPU。保留原版客户端互通及 Windows／Linux 边界。

第一步沿原版单机同步／TCP房主独立线程的结构实施，原版混合客户端及Linux行为仍未认证。复杂负载迁移、跨角色原子保存及集群部署不在本次改造范围。
