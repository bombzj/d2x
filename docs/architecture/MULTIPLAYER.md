## 1. 目标、范围与不可退让的边界

目标是同一套客户端完整消费原 1.13c MCP／D2GS，由原服或自研服务端承担权威规则。先形成可靠的资料片普通非 Ladder PvE，再逐步完成七职业、五幕三难度、多人协作／交易／PvP、独立服务端及扩展模式。不能把“能进入地图”“有技能树”“能解码物品”“有消息入口”当作对应模块完成。

1. **一套客户端。** 选角、入局、输入、UI、世界副本、动画、音效及退局共用 RealmFrontend → RealmSession → Remote* → SceneController／SceneView。自研服务端接同版本原包，只把 TCP 换为内存字节队列；LAN 与原服也走相同 TCP 客户端。账号连接编排可以不同，游戏客户端不得新增自研专用玩法分支或协议。
2. **服务端权威。** 客户端不结算命中、掉落、消耗、成长、任务资格、奖励或存档；未知事实保留未知。自研服务端不通过弱化客户端原服支持、伪造客户端状态或本地 fallback 补齐缺口。
3. **领域拥有状态。** GameInstance 只组装与调度，GameHost 只编排实例，hosting 负责协议、内容准备、存储及连接；玩法由各自子系统负责。不能把新功能继续堆入会话、宿主或万能事件处理器。
4. **共用原地图。** 服务端与客户端使用同一 NativeMapGenerator、原表及生成／reveal 公共函数，运行状态分别持有；不传自定义地图快照替代原包，不另造服务端地图算法。
5. **先迁旧规则，再补证据。** 先读 master 已做的单机实现与当前纯函数，迁用可用规则；耦合 GameSession 的部分重构后接领域。缺漏／可疑行为才针对性核对本地 reference、当前 MPQ 和原 1.13c。参考附带表不能代替当前 MPQ；不整树恢复旧执行器。
6. **客户端修改以原版证据为边界。** 能由服务端输出正确原包完成的功能只改服务端。用户已授权有参考依据、匹配原版的公共层提取与客户端修复；这同样适用于职业技能迁入。每处修改须记录原包／MPQ／原函数证据，保留本人已知值与其他玩家未知值的差别。为了兼容自研服务端单独改客户端或发私有包不在授权内；证据不足的行为先暂缓并单独确认。
7. **不静默降级。** 未实现规则显式暂缓／拒绝，不用普通攻击代替技能，不漏扣条件后发奖励。唯一已授权敌对替身是沉沦魔，保留真实身份并明确标识，不能计为该怪物完成；中立单位不可替换。
8. **可移植与可保存。** C++20／CMake 同时保持 Windows／Linux 路径，玩法不读取 MPQ、Win32、设备、GPU、socket 或文件。D2S 属于服务端；语义变化同步格式支持范围、规则指纹与 SAVES，旧档不静默迁移。

原资源／reference／mvp／旧包保留，运行产物、存档及参考仓库不纳入源码提交。D2R 新规则、新素材及私有联网协议不属于本计划。

## 2. 实施状态

### 2.1 统一状态口径

每项分别记录客户端 C、服务端 S 和证据 V，不能用一个“已完成”覆盖三者。

| 状态 | 定义 |
| --- | --- |
| 未接 | 没有可用端到端实现；有类型、面板、数据导入或 stub 仍可属于未接 |
| 部分 | 已有具体可执行范围，同时存在明确的规则、协议、生命周期或表现缺口 |

| V1 构建 | 对应源码已构建／打包，不代表可玩或规则正确 |

## 3. 工作台账与单项完成标准

### 3.1 拆分粒度

本表是总计划，不把数百项功能压成“技能完成”“怪物完成”。进入对应阶段时，在已有负责模块／专题中维护逐项台账，不另建重复的总表。

| 台账 | 最小条目及必填范围 |
| --- | --- |
| 技能 | 当前 MPQ 每个可学习技能ID／名称；另列普通攻击、物品技能、佣兵／怪物技能。当前表每职业30项，实际枚举以MPQ为准 |
| 怪物 | MonStats家族及实际类型、攻击槽／技能、难度／精英变体、特殊身份；普通、冠军、暗金、超级暗金、幕首领分开 |
| 地图 | 每个区域的生成／房间／出口／人口／物件／任务关联；生成器证据与运行世界证据分栏 |
| 任务 | 五幕27项，以及欢迎／旅行／牛场／扩展事件；个人位、本局位、难度、资格、奖励、重入分开 |
| 物品／服务 | 操作×位置／来源×关键属性，例如鉴定卷轴与Cain、普通修理与充能修理、背包与佣兵装备 |
| 协议 | 用户动作 → C2S及子命令 → 领域提交 → 必需S2C → 副本／UI消费 → 拒绝／超时／重入 |

每行记录：稳定ID、C状态、S状态、V证据、现有函数／旧master来源、当前MPQ／原协议依据、依赖、缺口、下一个可交付范围。不能因为同家族一个案例通过就批量标记所有成员完成。

消息目录的 Implemented 只表示已开放的范围。0x38／0x4F必须按子操作展开；0x05等通用施法入口必须按技能／来源展开；AdmissionOnly不能代表增量已接。91种S2C并不是原版全部协议；未来佣兵／关系等可增加已核实的原包。也不要求服务端为了凑数同时发出所有等价包：记录实际合法输出方案，例如原字段宽度和弹体ClientSend条件，避免重复视觉。

### 3.2 每次实施流程

1. 明确一个可玩范围和失败边界，读取基线、对应模块、当前函数及master旧实现。
2. 对照旧规则与当前MPQ，记录Srv计算／Clt表现、来源、目标、帧、取整及随机所有者；有争议再查本地reference／原1.13c。
3. 先核实客户端对原服的实际支持。只有服务端缺失则直接接领域；客户端也缺时先取得逐项修改确认，并补齐原服端到端协议与表现，不能用自研两端互相迁就作为依据。
4. 迁移公共纯值／函数，准备MPQ规则；实现领域状态、事务、失败处理，再实现原包投影。保持正常命令与调试命令共用权威路径。
5. 阅读检查所有权、背压、重复请求、迟到消息、区域／角色代次、断线清理与保存；新函数不能依赖UI或让网络回调直接改人物。
6. 更新模块台账、协议状态、保存／指纹及BASELINE。获得授权后构建、打包、人工运行验证；未运行的完成状态停在V0／V1，不自动提交。

### 3.3 范围验收门槛

正常操作之外，按该功能实际涉及的边界覆盖：资源不足、背包／Cursor冲突、距离／视线／目标消失、动作取消、重复／迟到请求、死亡／换区／退局、事件背压、多人争用及保存失败。非幂等原请求没有私有事务号，不自动重发；内部结算发生标识与原协议分开。

需要客户端变更时，原D2GS验证与自研宿主验证分别记录；需要存档时确认退出／新进程重入及奖励不重复；需要多人时确认两端看到同一权威结果且只结算一次。证据包括包版本／源码状态、当前MPQ、种子／职业／等级／难度、步骤与实际状态；“accepted”“收到包”“画面出现”均不足以单独证明成功。没有授权或环境时保留“待运行”，不造通过结论。

## 5. 分阶段实施顺序

以下是推荐顺序与依赖，不按工期猜完成日期。每阶段先完成最小代表路径，再扩到台账声明范围；不能只做代表案例就关闭整阶段。P0后的待运行基线可以在未获冒烟授权时继续记录，实施不因此伪称已验收；依赖的源码与语义缺口则必须先解决。P10可在P3多人基础稳定后作为独立工作批前移，不要求等待全部内容完成；不等于本次授权并行agent或启动新任务。

- 以当前未提交工作区为起点核对六项事务／生命周期、原包长度和含义、暂缓行为，统一过期模块说明。

- 已有有限V2范围见基线。继续补资源／死亡／物件／NPC／旅行未运行边界，不能因代表案例成功关闭整项。
- 调试诊断优先补观察能力：操作结果、事务前后revision、效果来源／剩余时间、掉落暂缓、任务资格／奖励发生、门／传送点身份。修改类命令必须经领域，不能用“调试完成任务”替代真实击杀／交互验收。

完成条件：每个现有范围能找到客户端消费者、服务端提交点、原包和已知限制；没有用旧包证据冒充新功能通过。入口：[基线](../../BASELINE.md)、[内核](../modules/SERVER_SYSTEMS.md)、[协议](../modules/SERVER_PROTOCOL.md)、[调试管道](../development/DEBUG_PIPE.md)。
